# Project delivery

1. Read the current source of truth. Identify the outcome, owner, dependencies and constraints without inventing dates, commitments or assignees.
2. Split work by deliverable behavior. Give each task an owner when known, estimate with its basis, dependencies and observable acceptance criteria.
3. Make acceptance concrete: supported inputs and devices, output behavior, failure cases, required evaluation sample and release evidence. Define metric denominators and thresholds only when supported or explicitly proposed.
4. Separate prerequisite, implementation, verification and release work when their owners or dependencies differ. Avoid a task per file or layer.
5. Keep decisions in the project's existing decision log. Record the context, chosen option, important tradeoff and revisit condition.
6. Report completed work with links to commits, checks, artifacts or issues. Distinguish planned, in progress, blocked, executed and verified.
7. Before release, check the actual configuration, migration/recovery path, observability and ownership needed for the feature. Do not invent a universal compliance checklist.
8. Keep updates short: delivered behavior, evidence, blocker, next action and decision needed. Write in the team's language and preserve domain terminology.
9. Create or send external tasks, invitations and messages only when the user authorizes those actions.
